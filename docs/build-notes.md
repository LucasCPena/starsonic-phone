# Notas do build no Windows e no Linux

Como o Starsonic Phone é compilado e o que precisou de ajuste para o workflow ficar verde. A primeira parte é do app novo (a partir da 0.1.0: `windows/app` e `windows/ui`); a segunda, do app antigo (a série 0.0.1, o MicroSIP), que continua compilando enquanto `microsip/` existir; a terceira, do motor de ligações com o baresip (o do iPhone), que por enquanto só é compilado no Linux, para os testes; a quarta, do vídeo do PJSIP (o do Windows e o dos testes do motor no Linux); a quinta, dos patches que a PJSIP leva nos três builds que a compilam.

## App novo (0.1.0)

### Como compilar

Pré-requisitos: Visual Studio 2022 com "Desenvolvimento para desktop com C++", Git, Node.js 22, NSIS 3 e Windows PowerShell 5.1.

```powershell
.\build\Build-Deps.ps1 -WorkDir work            # pjproject 2.17, vcpkg e o SDK do WebView2 (uma vez; demora)
cd windows\ui; npm ci; npm run build; cd ..\..    # a interface em windows\ui\dist
.\build\Build-Windows.ps1 -WorkDir work -Version 0.0.0 -Channel estavel -OutDir out-novo
.\build\Build-Installer.ps1 -Version 0.0.0 -AppDir out-novo -OutDir dist -WorkDir work
.\tests\smoke\Test-WindowsApp.ps1 -AppDir out-novo
```

No CI, o job `ui` (Linux) faz o `npm ci`, o `npm run build` e o Playwright e publica a interface como o artefato `ui-dist`; o job `windows` baixa esse artefato para `windows\ui\dist` antes do `Build-Windows.ps1`.

### Ajustes

- **O SDK do WebView2 com versão fixa.** O `Build-Deps.ps1` baixa o NuGet `Microsoft.Web.WebView2` da versão do `build/deps.lock` (`webview2.version`), confere o SHA-256 do `.nupkg` (`webview2.sha256`) e guarda só os cabeçalhos e o `x86\WebView2LoaderStatic.lib` em `work\webview2`, com um arquivo `VERSION`. O `Build-Windows.ps1` recusa um `work\webview2` de outra versão. Para trocar a versão, mude as duas linhas do `deps.lock` juntas: isso refaz o cache das dependências (uns 13 minutos).
- **O bootstrapper do WebView2 com cache próprio.** O instalador leva o `MicrosoftEdgeWebview2Setup.exe` (Evergreen). O endereço curto da Microsoft (`fwlink`) troca de arquivo a cada versão, então o `deps.lock` guarda o endereço do próprio arquivo, a versão e o SHA-256 (`webview2Bootstrapper`). O `Build-Installer.ps1` baixa para `work\webview2-bootstrapper`, confere o SHA-256 e a assinatura da Microsoft e só baixa de novo se o arquivo guardado não bater. No CI, essa pasta tem um cache separado, com a chave pelo SHA-256 (`build/cache_keys.py`): assim, quando a Microsoft tira o endereço do ar, o build e o release continuam com o arquivo guardado, e trocar o bootstrapper não refaz o pjproject nem o vcpkg. Sem o cache e com o endereço fora do ar, o build para com o erro do download ou do SHA-256: ache o endereço novo (o `fwlink` leva a ele), confira a assinatura e atualize as três linhas.
- **O build de teste (`-TestHooks`).** O `Build-Windows.ps1 -TestHooks` compila com `STARSONIC_TEST_HOOKS=ON` (saída em `out-novo-teste`, e o `Build-Installer.ps1` gera dele um instalador em `dist-teste`, com o mesmo `.nsi`). Só nesse build valem: `STARSONIC_PERFIL` (o texto da variável toma o lugar do perfil embutido: o registrador falso na 5060 por UDP, sem STUN e sem SRTP, com PCMU e PCMA), `STARSONIC_SOM_NULO` (o motor no dispositivo nulo do PJSIP), `STARSONIC_TRAVAR_SAIR` (o Sair trava a thread de comandos, para conferir o fechamento com limite), `STARSONIC_SENHA_ADMIN_TESTE` (rc.3: a área do administrador entra com o texto da variável no lugar da senha de verdade, que nunca vai ao CI), o `--teste-internet off|on` (rc.3: com o app aberto, a instância única entrega o pedido e o monitor de rede passa a ver a internet fora, como a rede que cai, ou volta à visão de verdade), `STARSONIC_TESTE_DNS_MS` (rc.3: o intervalo do monitor de rede em milissegundos, de 100 a 30000, com cada resultado do teste DNS no diagnóstico; a fumaça com o servidor por nome) e as ferramentas do desenvolvedor do WebView2. A fumaça (`Test-InstalledApp.ps1` e `windows_smoke.py`) usa esse build porque o runner do GitHub não tem placa de som: sem nenhum dispositivo, o PJSIP recusa a ligação (`PJMEDIA_EAUD_NODEFDEV`). O instalador de publicação não tem esses ganchos e é conferido pela marca estrita, pelo `Test-Installer.ps1` e pelo ensaio da rc.7.
- **Os ganchos de teste fora do exe de publicação (Ruling 19).** O passo "Sem os ganchos de teste no app novo" roda o `build/check_test_hooks.py` no `out-novo\StarsonicPhone.exe`: ele procura o nome de cada gancho (as variáveis e a opção acima), em ASCII e em UTF-16LE, e reprova o build se achar um (o `STARSONIC_SENHA_ADMIN_TESTE` num release abriria a área do administrador com qualquer senha). O passo seguinte roda o mesmo script com `--presentes` no `out-novo-teste\StarsonicPhone.exe`: no build de teste a busca tem de achar todos os nomes, senão ela não acharia um que vazasse. A lista dos nomes fica no script; o `tests/python/test_check_test_hooks.py` confere que ela tem os de todo `#if STARSONIC_TEST_HOOKS` do `windows/app/src` e que esta nota cita cada um. Um gancho novo entra no script e nesta lista.
- **O DevTools da fumaça.** A fumaça abre o app com `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333 --autoplay-policy=no-user-gesture-required` e liga o Playwright para Python pelo CDP. A variável toma o lugar dos argumentos que o app passa ao WebView2, por isso leva também o `--autoplay-policy` do app (sem ele, o toque pode sair mudo). O `setup-python` 3.12 do job `windows` é para o Playwright ter as versões de `tests/smoke/requirements-windows.txt`.
- **A conferência de marca abre o instalador por dentro.** O NSIS (`SetCompressor /SOLID lzma`) guarda os textos das páginas, as caixas de mensagem e os arquivos num bloco LZMA. Procurar "MicroSIP" nos bytes do `setup.exe` não acharia nada. O `check_branding.py --instalador` lê o cabeçalho do NSIS, descomprime o bloco inteiro (LZMA ou zlib) e procura no que está dentro; um instalador cortado, estragado no meio ou com lixo no fim reprova por não abrir. No Windows, o passo "Teste da verificação de marca com um instalador LZMA de verdade" gera instaladores pelo `makensis` (um com "MicroSIP" numa caixa de mensagem) e confere que o check reprova o certo; no Linux, sem o `makensis`, esses testes ficam de fora.
- **O pacote de fontes com os pacotes do npm.** A interface empacotada (`ui\app.js`) leva o Preact, então a GPL pede o código dele junto. O `Make-SourceBundle.ps1` põe em `npm-packages/` os `.tgz` dos pacotes do `windows/ui/package-lock.json` que não são `dev` (hoje só o `preact`), baixados do `resolved` do lock e conferidos pelo `integrity` (SHA-512). O `LEIA-ME-FONTES.txt` diz como montar o `node_modules` sem internet. O `package-lock.json` tem uma chave vazia (`""`) que o `ConvertFrom-Json` do Windows PowerShell 5.1 recusa; o script troca essa chave por `"(raiz)"` antes de ler o lock. O passo "Teste do pacote de fontes" roda o script em todo build sem versão (cerca de 1 minuto) e confere o zip pelo `Test-SourceBundle.ps1`; por isso todo build do Windows depende do registro do npm no ar.
- **`needs: ui`.** O job `windows` espera o job `ui`, porque o app novo leva a interface (o artefato `ui-dist`). Um teste do Playwright que falha (ou um instável) pula o job `windows` inteiro: um teste instável na interface tem de ser corrigido logo, senão nada do Windows roda.
- **Os avisos das licenças MIT.** O `build.mjs` copia `node_modules/preact/LICENSE` para `dist/assets/preact-LICENSE.txt`, ao lado do `OFL.txt` da fonte. Desde a rc.4, ele copia também as licenças do miniz e do nlohmann/json, que vão dentro do `StarsonicPhone.exe`, como vieram em `starsonic/third_party`: `dist/assets/miniz-LICENSE.txt` e `dist/assets/nlohmann-json-LICENSE.txt`. O instalador leva a pasta `ui\` inteira, e o `screens.spec.ts` confere os três avisos.
- **O `connect-src 'self'` da interface (rc.4).** A Content-Security-Policy do `windows/ui/index.html` passou de `connect-src 'none'` para `connect-src 'self'`, porque a página lê o `assets/toque.wav` com `fetch` para tocar a recebida. Com o `'none'`, o `fetch` era bloqueado, e a recebida caía sempre nos 425 Hz, sem erro nenhum. O `'self'` só deixa a página ler os arquivos do próprio app (a pasta `ui\`, servida com `DENY_CORS`). O `aviso.html` continua com `'none'`: o aviso do canto nunca toca.
- **A URL com a versão.** O `build.mjs` põe os 12 primeiros dígitos do SHA-256 do conteúdo na URL do `app.js`, do `aviso.js` e do `app.css` (`app.js?v=<hash>`), e o app abre `index.html?v=<versão>` e `aviso.html?v=<versão>`. Assim o cache do WebView2 nunca serve a interface de uma versão anterior.
- **Os literais ASCII também em `windows/`.** O `check_source_text.py` passou a conferir `windows/` (os `.cpp`, os `.h` e o `.rc`): o MSVC lê os fontes sem BOM na página de código do Windows.
- **O `LegacyCrypto.cpp` fora do app antigo.** A rotina que decifra as senhas da rc.7 mora em `starsonic/win`, mas é C++17 e só do app novo; o `starsonic/starsonic.targets` a tira do glob `win\*.cpp` do app antigo, que compila em C++14 com o cabeçalho pré-compilado.
- **O instalador antigo saiu do CI.** O job `windows` ainda compila o app antigo e roda os testes de fumaça dele, mas só gera o instalador do app novo. O `release.yml` confere que o instalador tem o `StarsonicPhone.exe`, a `ui/index.html`, a `ui/aviso.html` e o bootstrapper do WebView2 antes de publicar.
- **A publicação pelo `workflow_dispatch`.** Nas sessões do agente (o Claude Code, que sai pela internet por um proxy), o `git push` de uma tag falha. Por isso as versões saem pelo disparo à mão do `release`, que cria a tag no commit escolhido: `gh workflow run release.yml --ref main -f versao=0.1.0-rc.1`. O ensaio da atualização da rc.7 também é à mão: `gh workflow run build.yml --ref main -f ensaio-atualizacao=true`.

## App antigo (MicroSIP, série 0.0.1)

### Como compilar

Pré-requisitos: Visual Studio 2022 com "Desenvolvimento para desktop com C++" e "MFC para v143 (x86 e x64)", Git e Windows PowerShell 5.1.

```powershell
.\build\Build-Deps.ps1 -WorkDir work      # pjproject 2.17 + vcpkg (uma vez; demora)
.\build\Build-App.ps1 -WorkDir work -Version 0.0.0 -Channel estavel -ProfileFile branding\perfil.ini -OutDir out
.\tests\smoke\Test-StartStop.ps1 -AppDir out
```

As versões das dependências estão em `build/deps.lock`; a configuração do pjproject, em `build/config_site.h`.

O projeto do MicroSIP espera estar dentro da árvore do pjproject (`..\pjlib\include`, `..\build\vs\…`). Por isso o `Build-App.ps1` espelha `microsip/`, `starsonic/` e `branding/` para dentro de `work\pjproject\` antes de compilar.

### Ajustes

- **Toolset v143 na linha de comando do pjproject.** Os projetos do pjproject 2.17 fixam `PlatformToolset` v140, que não existe no VS 2022; o `Build-Deps.ps1` passa `/p:PlatformToolset=v143`, como o próprio CI do pjproject faz.
- **Cabeçalhos do vcpkg via `CL`.** O pjproject não tem como receber diretórios de include extras para OpenSSL, Opus e bcg729; o `Build-Deps.ps1` define `CL=/I<vcpkg>\installed\x86-windows-static\include` durante a compilação.
- **`chkstk_ms.lib` vazio.** O projeto do MicroSIP lista essa biblioteca do MinGW (usada pelas builds MinGW de Opus/bcg729 do MicroSIP). Com as dependências compiladas pelo MSVC ela não é necessária; o `Build-Deps.ps1` cria uma biblioteca vazia em `pjproject\third_party\lib\`.
- **`TargetName` na linha de comando.** O `starsonic.targets` entra no fim do `.vcxproj` (edição E3), depois das propriedades que derivam do nome do alvo; o `Build-App.ps1` passa `/p:TargetName=StarsonicPhone` para o nome valer desde o começo da avaliação do projeto.
- **Limpeza do cache.** Depois de compilar, o `Build-Deps.ps1` apaga as pastas `output` do pjproject e `buildtrees`/`downloads`/`packages` do vcpkg, para o cache do Actions ficar pequeno.
- **Código-fonte das dependências na publicação.** Como o cache não guarda os downloads do vcpkg, o `Make-SourceBundle.ps1` (só nas versões publicadas) baixa de novo o código-fonte das portas com `vcpkg install --only-downloads --binarysource=clear`, numa pasta de instalação vazia, sem compilar nada.
- **Instalador.** O `Build-Installer.ps1` gera a lista dos arquivos instalados a partir de `out\` (sem o PDB), para o desinstalador apagar exatamente os mesmos. O CI instala o NSIS 3.10 pelo Chocolatey só se ele não estiver na imagem.
- **`PJMEDIA_AUD_MAX_DEVS`.** O MicroSIP 3.22.16 usa o nome antigo do limite de dispositivos de áudio; no pjproject 2.17 ele se chama `PJMEDIA_AUD_DEV_MAX_DEVS`. O `config_site.h` define o nome antigo como apelido do novo (erro C2065 em `mainDlg.cpp`, `microsip.cpp` e `SettingsDlg.cpp`).

## Motor com o baresip (Linux)

O `SipEngine` do iPhone (`starsonic/phone/baresip/`) usa a libre e o baresip 4.12.0 e a libg722 1.2.8 (nenhum sob GPL ou LGPL, spec 10), estáticos, nas versões e commits da chave `baresip` do `build/deps.lock`, com os módulos `g711`, `libg722`, `opus`, `srtp`, `stun` e `mixminus`. O módulo `g722` do baresip (usa a spandsp, sob LGPL) nunca entra. No Linux ele passa pelos testes do contrato do motor (o `phone_tests_baresip`, contra o registrador falso).

### Como compilar

Pré-requisitos: Git, CMake, g++, Python 3, `libssl-dev`, `libopus-dev` e `zlib1g-dev`.

```bash
bash build/baresip/build-linux.sh work/baresip-src baresip-linux   # uma vez por versão do deps.lock
cmake -S tests/phone -B build-phone-baresip -DBARESIP_PREFIX="$PWD/baresip-linux"
cmake --build build-phone-baresip -j 4
ctest --test-dir build-phone-baresip --output-on-failure
```

O `-DBARESIP_PREFIX` e o `-DPJPROJECT_PREFIX` (o `phone_tests`, com o PJSIP) podem ir no mesmo build; o `call_controller_tests` sai com qualquer um dos dois. No CI, o job `core-tests` do `build.yml` faz o mesmo, com o `baresip-linux` num cache cuja chave muda com o `build/deps.lock` e com o `build/baresip/`.

### Ajustes

- **Um `.a` só, com os módulos.** No `STATIC` do baresip 4.12, cada módulo é uma biblioteca OBJECT do CMake, e os objetos dele vão dentro do `libbaresip.a`; o install do baresip pede o executável e os testes dele, que o motor não usa. O script compila só a biblioteca e a copia com o `ar -M` para `lib/libstarsonic-baresip.a`, ao lado da `libre.a` e da `libg722.a`, que o link põe entre `--start-group` e `--end-group` (uma chama a outra). As bibliotecas do sistema vão em `lib/starsonic-baresip-libs.txt` (`ssl crypto opus z pthread m dl`).
- **A conferência dos módulos.** São duas, as duas contra a lista `baresip.modules` do `deps.lock`. O script confere o arquivo: o baresip deixa de fora, sem erro, o módulo que não acha a biblioteca dele (o `opus` sem o `libopus-dev`, por exemplo), então o script procura com o `nm` o `exports_<módulo>` de cada um no `libstarsonic-baresip.a` e sai com erro se faltar um ou se sobrar um que não está no `deps.lock`. O teste "the baresip engine loads the modules of build/deps.lock, in order" (`tests/phone/test_engine_baresip.cpp`) confere o código: a lista que o motor carrega (`BaresipLoop::Modules()`, a constante `kModules` do `BaresipLoop.cpp`) tem de ser a do `deps.lock`, nome a nome e na ordem. O teste roda em todo build; o script, no CI, só quando falta o cache do `baresip-linux`, cuja chave não leva o `BaresipLoop.cpp`.

## O vídeo

A videochamada é só do app novo do Windows (spec da videochamada, seção 6.2). O PJSIP do Windows e o dos testes do motor no Linux compilam com o vídeo. O do Android (`build/android/config_site.h`) segue sem vídeo, e o motor do iPhone (o baresip) não tem vídeo. O `SipEngine::VideoCodecs()` lista os codecs de vídeo ligados, como `H264/97` e `VP8/100`; sem o vídeo, a lista é vazia.

### As opções do Windows (`build/config_site.h`)

- **`PJMEDIA_HAS_VIDEO 1`** liga o vídeo na PJSIP. Ao iniciar, o pjsua cria o subsistema de vídeo e registra as fábricas dos codecs e das câmeras.
- **`PJMEDIA_VIDEO_DEV_HAS_DSHOW 1`** traz as câmeras pela DirectShow do Windows (o `dshow_dev.c`, com a `third_party/BaseClasses` do pjproject, que já entra na `libpjproject`). O `dshow_dev.c` pede o `strmiids`, o `quartz` e o `rpcrt4` do Windows SDK por `#pragma comment`, e o link do app os lista também.
- **`PJMEDIA_VIDEO_DEV_HAS_SDL 0`** deixa de fora as janelas do SDL.
- **`PJMEDIA_VIDEO_DEV_HAS_CBAR_SRC 0`** tira a câmera de teste da PJSIP (barras coloridas), que apareceria na lista das câmeras da pessoa.
- **`PJMEDIA_HAS_FFMPEG 0`** deixa o FFmpeg de fora.
- **`PJMEDIA_HAS_VPX_CODEC 1`** e **`PJMEDIA_HAS_VPX_CODEC_VP9 1`** trazem o VP8 e o VP9 pela libvpx, a porta `libvpx` do vcpkg (a versão fica no `build/deps.lock`, conferida pelo `Build-Deps.ps1` como as outras portas). O `vpx.c` da PJSIP pede o `vpx.lib` por `#pragma comment`, e o link do app o lista também; a pasta `lib` do vcpkg já está no link dos dois apps.
- **`PJMEDIA_HAS_OPENH264_CODEC 1`** traz o H.264 pelo OpenH264. A PJSIP compila com os cabeçalhos da API (abaixo). As quatro funções que ela chama vêm do adaptador do app (`windows/app/src/OpenH264Shim.cpp`), que as repassa ao módulo da Cisco, carregado em tempo de execução pelo caminho completo (spec da videochamada, seção 6.3). O `openh264.cpp` da PJSIP pede o `openh264.lib` por `#pragma comment`, e o link do app o ignora (`/NODEFAULTLIB:openh264.lib`): o `.exe` não depende do módulo para abrir. O binário da Cisco nunca entra no app, e a porta `openh264` do vcpkg nunca entra no `deps.lock` (o `tests/python/test_deps_lock.py` confere).
- **`PJMEDIA_HAS_LIBYUV 1`** usa a libyuv do próprio pjproject (`third_party/yuv`, que já entra na `libpjproject`) para converter e escalar as imagens.

**Por que sem o SDL e sem o FFmpeg.** O SDL é o que desenha a imagem em janelas próprias, no jeito do MicroSIP. No app novo, a imagem vai para a página (o WebView2) por um dispositivo de saída nosso (spec da videochamada, seções 6.2 e 6.4), e o SDL seria uma biblioteca a mais, sem uso. O FFmpeg só acrescentaria o H.263+, que ficou fora do escopo: o H.264 vem do OpenH264, o VP8 e o VP9 vêm da libvpx, e a libyuv converte as imagens.

**Os cabeçalhos do OpenH264.** Os quatro cabeçalhos da API (`starsonic/third_party/openh264/include/wels/`) vieram sem mudança da tag `v2.6.0` de `cisco/openh264`, com o `LICENSE` (BSD de 2 cláusulas) da mesma tag; o `README.md` da pasta diz o commit. Só a API entra no repositório. O `Build-Deps.ps1` põe a pasta no `CL` da compilação do pjproject, ao lado dos cabeçalhos do vcpkg. A versão é a do `deps.lock` (`openh264.version`), e o `test_deps_lock.py` confere que o `codec_ver.h` é dela. A chave do cache das dependências do Windows leva o `deps.lock`, e não os cabeçalhos: troque os dois juntos.

### O módulo H.264 da Cisco (OpenH264)

A licença da Cisco deixa o app baixar o binário dela para o computador da pessoa, mas nunca levá-lo dentro do app ou do instalador. O app baixa `openh264-2.6.0-win32.dll.bz2` de `http://ciscobinary.openh264.org/` (o servidor de binários da Cisco não tem HTTPS; o `HttpGetPinned` só aceita esse endereço, sem seguir redirecionamento) e só usa o arquivo se as duas impressões (SHA-256) fixadas baterem: a do `.bz2` e a do `.dll` descompactado (`H264Module::Ensure`, com o teto de 4 MiB comprimidos e 8 MiB descompactados; o `Bunzip2` usa a libbz2, a porta `bzip2` do vcpkg). A impressão do `.dll` é conferida de novo a cada abertura do app (`H264Module::Verify`). No app, o gancho `h264Ensure` (`windows/app/src/main.cpp`) grava o arquivo em `%LOCALAPPDATA%\Starsonic Phone\codecs` e só o carrega pelo caminho completo (`LoadOpenH264`) depois de conferir de novo; a desinstalação apaga essa pasta (`installer/StarsonicPhone.nsi`).

**A etapa 2 do vídeo ligou o download.** A opção `STARSONIC_H264_DOWNLOAD` do `windows/app/CMakeLists.txt` (padrão `ON`, e nenhum script do build a passa) decide se o app baixa e carrega o módulo: ela vira o `DesktopConfig::h264Download` do núcleo, e desligada o H.264 fica `desligado`, sem o gancho `h264Ensure`. Ela fica ligada em todo build porque o `release.yml` publica o instalador que o `build.yml` compila, e a licença do binário pede três coisas, que a etapa 2 trouxe junto com a opção: a chave "H.264 da Cisco" da pessoa (Configurações), o aviso "OpenH264 Video Codec provided by Cisco Systems, Inc." e o texto da licença na tela de Licenças (`windows/ui/assets/licencas-windows.txt`, com o OpenH264, a libvpx e a libyuv; os textos da libvpx e da libyuv estão em `starsonic/third_party/`). O `build/Test-OpenH264.ps1` do CI segue conferindo o binário fixado, à parte.

As impressões ficam em dois lugares que o `tests/python/test_deps_lock.py` confere iguais: o `openh264` do `build/deps.lock` (`version`, `url`, `file`, `bz2Sha256`, `dllSha256`) e o `starsonic/desktop/OpenH264Pin.h`. O passo "Módulo H.264 da Cisco" do job `windows` (`build/Test-OpenH264.ps1`, no PowerShell 7: `shell: pwsh`) começa pelo auto-teste da leitura do assinante (nomes de certificado falsos, montados no passo, têm de ser recusados, e os da Cisco, aceitos; um erro derruba o passo). Depois, baixa o binário verdadeiro, descomprime com as regras do app (`build/unpack_openh264.py`: um fluxo bzip2 só, nenhum byte depois do fim dele, até 4 MiB comprimidos e 8 MiB descomprimidos; senão, falha), mostra as duas impressões e exige a assinatura Authenticode da Cisco: o `Status` `Valid` e o `O` do certificado do assinante igual, por inteiro, a `Cisco Systems, Inc.` ou `Cisco WebEx LLC`. O `O` é lido pela estrutura do nome do certificado (os RDNs, o OID `2.5.4.10`), nunca pelo texto do `Subject`, e tem de ser um só. O passo também exige o recurso de versão do `.dll` da `openh264.version`, compara as impressões com o `deps.lock`, guarda o texto da licença do binário como o artefato `openh264-licenca` (uma diferença dos bytes do `starsonic/third_party/openh264/BINARY_LICENSE.txt`, pelo SHA-256, só avisa) e confere que o app empacotado e o instalado pela fumaça não têm nenhum `openh264*.dll` (uma pasta que não dá para ler falha). Um site da Cisco fora do ar só avisa.

**Como trocar a versão fixada.**
1. Troque os cabeçalhos da API (`starsonic/third_party/openh264/include/wels/`, da tag nova de `cisco/openh264`) e o `openh264.version`, `url` e `file` do `deps.lock` (o `url` e o `file` levam a versão: o teste confere). Deixe `bz2Sha256` e `dllSha256` vazias.
2. Faça o push: o passo da Cisco só avisa (`::warning::`) com as duas impressões do binário novo, e mostra a linha do Authenticode. Confira que o `Status` é `Valid` e o `Subject` é da Cisco. Nunca fixe impressões que não passaram por essa assinatura. As DLLs do OpenH264 são assinadas pela **Cisco WebEx LLC** e publicadas pela Cisco Systems: o passo aceita o único `O` do nome do certificado do assinante, lido pela estrutura do nome, igual, por inteiro, a `Cisco Systems, Inc.` ou `Cisco WebEx LLC`, nada mais (um nome parecido, um segundo `O` ou um `O=` dentro das aspas de outro campo não valem). E o recurso de versão do `.dll` (`FileVersion` ou `ProductVersion`) tem de começar com o `openh264.version` do `deps.lock`, para um `.dll` assinado de outra versão não passar.
3. Copie as duas impressões para o `deps.lock` e o `OpenH264Pin.h`, e o texto do artefato `openh264-licenca` para o `BINARY_LICENSE.txt`, se mudou, com os bytes como vieram (o `.gitattributes` tira o arquivo da troca de fim de linha, e o passo compara os bytes). Faça o segundo push: agora o passo falha se as impressões diferirem.
4. As pastas `%LOCALAPPDATA%\Starsonic Phone\codecs` de quem já usa o app perdem o arquivo da versão velha sozinhas: o `Ensure` apaga todo `openh264-*.dll` que não é o do pino e todo `*.part`.

### O Linux dos testes (`build/linux/`)

O `build/linux/config_site.h` liga o `PJMEDIA_HAS_VIDEO` e, como no Windows, o `PJMEDIA_HAS_VPX_CODEC_VP9` (o VP9 vem desligado na PJSIP, e o teste "the codec settings order and filter the offer" o oferece). A câmera dos testes é a de barras coloridas da PJSIP, que vem ligada por padrão. O `build-pjproject.sh` chama o `configure` com `--enable-video --with-vpx=/usr --with-openh264=/usr --disable-sdl --disable-ffmpeg --disable-v4l2`: o VP8 e o VP9 pela libvpx do sistema (`libvpx-dev`), o H.264 pelo OpenH264 do sistema (`libopenh264-dev`, só dos testes e nunca publicado) e a libyuv do pjproject. Sem o SDL, o FFmpeg e o Video4Linux. Os dois pacotes entram no passo "Dependências do sistema" do job "Motor de ligações (Linux)" do `android.yml`. Sem eles, o `configure` deixa os dois codecs de fora sem erro, e o teste "the video build offers H264 and VP8" (`tests/phone/test_engine_video.cpp`) falha.

### A sala de vídeo

A sala (até 6 pessoas: quem monta e mais 5) monta o mosaico dos convidados com o `I420Scale` da libyuv (`starsonic/phone/RoomMosaic.cpp`, inteiro dentro de `#if PJMEDIA_HAS_VIDEO`: o Android compila o arquivo vazio).

- **Os cabeçalhos da libyuv.** A libyuv já está dentro da `libpjproject` do Windows (o conversor da PJSIP a usa), mas o `make install` não instala os cabeçalhos dela. No Linux dos testes, o `build/linux/build-pjproject.sh` copia o `third_party/yuv/include/libyuv.h` e a pasta `libyuv/` para `$PREFIX/include/`; a biblioteca já entra no link pelo `Libs.private` do `libpjproject.pc` (o `tests/phone/CMakeLists.txt` usa o `PJ_STATIC_LDFLAGS`). No Windows, o `windows/app/CMakeLists.txt` põe o `${PJPROJECT_DIR}/third_party/yuv/include` nos includes. Como o script mudou, a chave do cache do pjproject do Linux muda, e o job `android` o refaz uma vez.
- **As 8 ligações.** O `PJSUA_MAX_CALLS` passa de 4 para 8 no `build/config_site.h` (o Windows) e no `build/linux/config_site.h` (os testes): 5 convidados, a ligação de fora e folga. Como o `config_site.h` entra no pjproject, o job do Windows refaz as dependências uma vez.
- **Por que o Android fica com 4.** O `build/android/config_site.h` não muda: o Android não tem vídeo, então não monta sala, e o motor dele segue com as ligações de hoje.

### Ajustes

- **O app antigo com a PJSIP do vídeo.** O app antigo (o MicroSIP, edição Lite, sem vídeo) liga a mesma `libpjproject`, e o `pjsua_init` dele passa a trazer o `openh264.cpp` da PJSIP, que pede o `openh264.lib` e as quatro funções do OpenH264. ## Os patches da PJSIP

A PJSIP do `build/deps.lock` leva os patches de `build/patches/pjproject/`, feitos pelo `git format-patch` contra o commit fixado, nos três builds que a compilam: o `build/Build-Deps.ps1` (o Windows), o `build/linux/build-pjproject.sh` (os testes do motor) e o `build/android/build-deps.sh` (o Android). Cada um põe o pjproject no commit fixado, volta os arquivos versionados ao commit (`git reset --hard`: a pasta reaproveitada nunca fica com um patch aplicado duas vezes) e aplica cada `*.patch` com o `git apply`, na ordem dos nomes; um patch que não aplica para o build com o nome dele e o commit. As chaves dos caches cobrem a pasta (o `deps` do `build/cache_keys.py`, o `pj-linux` e o `android-deps` do `android.yml`): um patch novo ou mudado refaz a PJSIP uma vez em cada job. Os pacotes de código-fonte (o `build/Make-SourceBundle.ps1` e o `build/android/make_source_bundle.sh`) levam a PJSIP como veio do repositório e, ao lado, a pasta `pjproject-patches/`, com o LEIA-ME dizendo como aplicar: a licença da PJSIP pede o código das mudanças.

- **`0001-vid-stream-para-o-envio-antes-da-trava.patch`** (a sala de vídeo, 12/11/2026). Toda stream de vídeo tem uma thread de envio, porque o controle de taxa padrão do pjsua, que o motor mantém, é o `PJMEDIA_VID_STREAM_RC_SEND_THREAD`. Na 2.17, o `pjmedia_vid_stream_destroy` pega a trava do grupo da stream e, com ela presa, junta essa thread (o `detach_send_manager`), e a thread, depois de mandar cada pacote, pega a mesma trava para devolver o buffer. Um encerrar que chegava com um pacote em envio (desligar, pôr em espera, um re-INVITE que refaz a stream) travava o motor para sempre. O patch para e junta a thread antes de pegar a trava; o resto do destroy fica igual. No Android, sem o vídeo, o código do `vid_stream.c` fica todo de fora (o arquivo inteiro está dentro do `#if PJMEDIA_HAS_VIDEO`), mas o patch vai igual: a PJSIP é a mesma nos três. O teste é o "the video stream destroy returns while its send thread is still sending a packet" (`tests/phone/test_pjsip_vid_stream.cpp`): uma stream sozinha, com um transporte que segura o pacote enquanto outra thread chama o destroy; sem o patch, ele falha pelo prazo de 5 s.

**Numa PJSIP nova.** Troque o commit no `deps.lock` e rode o `build/linux/build-pjproject.sh`. Um patch que não aplica para o build: refaça-o contra o commit novo (o mesmo nome) ou veja se ainda é preciso. Para saber se a própria PJSIP já corrigiu, compile-a uma vez sem o patch (tire o arquivo da pasta) e rode o teste dele: se passar, a PJSIP corrigiu, e o patch sai (sem patch nenhum, apague a pasta: os builds e os pacotes de fontes seguem sem ela). Se falhar, o patch continua. No `0001`, leia também o `vid_stream.c` novo: o gerente de envio (`send_manager`) ainda é um por stream na 2.17 (o comentário da PJSIP diz que pode passar a ser dividido); se uma PJSIP nova o dividir entre as streams, parar a thread dele no destroy de uma pararia o envio das outras, e o patch precisa ser refeito.
